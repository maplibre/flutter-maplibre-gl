FFI engine benchmarks

We benchmarked the experimental dart:ffi engine against the current platform-view implementation ("stable") on the same Android device: 63 measured runs across 7 scenarios, offline on warmed tile caches, three iterations each. The short version: with its engine isolate enabled, the FFI engine matches the stable engine's smoothness and is dramatically faster everywhere your app talks to the map — live data, queries, startup — at about half the CPU cost. A follow-up optimization round (frame loop aligned to the display's vsync, tuned gesture pipeline) then closed the one remaining gap: gesture render throughput is now on par with stable too.

The gesture gap, before and after vsync alignment

Map render throughput during touch gestures (frames per second, 90 Hz panel). The first round left the stable engine an 8–16 % edge here (grey bars). Aligning the FFI frame loop to the display's vsync (Android Choreographer) and tuning the gesture pipeline closed it: the re-run full suite puts FFI within ~2 % of stable everywhere except pinch (−9 %). A control run confirmed the mechanism — pacing frames with a plain timer at the same rate but out of phase with the display costs 30–36 % throughput.

Method, in one paragraph

Modeled on MapLibre Native's own world-tour benchmark: one discarded warm-up pass fills the tile caches, then three recorded iterations run fully offline with the engine order rotated per iteration, a thermal gate plus cooldown between runs, and every run started cold. Metrics are frame-time distributions (not averages), engine render stats, API latencies, CPU, and memory. One device so far: Xiaomi 11 Lite 5G NE (90 Hz, Android 14), profile build.

Caveats: stable-vs-FFI deltas mix transport and renderer effects (Vulkan vs OpenGL ES); the FFI-with-isolate vs FFI-without comparison is confound-free. Results are from a single mid-range device; absolute numbers will vary, directions should hold.
